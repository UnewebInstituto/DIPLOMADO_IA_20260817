## No hay una unidad fija de "tamaño de token"

Un token no se mide en caracteres ni en palabras de forma fija — es la unidad mínima en la que el **tokenizador** del modelo divide el texto, y su tamaño varía según el algoritmo y el idioma.

## Cómo se construyen los tokens

La mayoría de los modelos actuales (Claude, GPT, Gemini) usan variantes de **compresión por pares de bytes (BPE)** o algoritmos similares (como SentencePiece). El proceso, en esencia:

1. Se parte de caracteres o bytes individuales.
2. El algoritmo analiza un corpus enorme de texto y encuentra los pares de símbolos que aparecen juntos con más frecuencia.
3. Esos pares frecuentes se fusionan en un solo token nuevo.
4. Se repite el proceso miles de veces hasta llegar a un vocabulario de tamaño fijo (típicamente 30.000–250.000 tokens).

El resultado es que las secuencias de caracteres muy comunes (como `"the"`, `"ing"`, o en español `"ción"`, `"que"`) terminan siendo un solo token, mientras que palabras raras o poco frecuentes se dividen en varios tokens más pequeños, letra por letra si hace falta.

## Reglas prácticas de tamaño (aproximadas, no exactas)

| Idioma | Aproximación |
|---|---|
| Inglés | ~4 caracteres por token, o ~¾ de palabra por token |
| Español y otros idiomas latinos | Un poco menos eficiente que el inglés (~20-30% más tokens para el mismo texto), por tener menos representación en el vocabulario de entrenamiento |
| Código fuente | Varía mucho según el lenguaje y el nivel de indentación/símbolos |
| Números, símbolos raros, emojis | A menudo un token por carácter o incluso más de uno |

## Relación directa con tu práctica de n8n

Esto es justo lo que estabas midiendo en el Nodo 5 con Gemini: en `usageMetadata`, `promptTokenCount` y `candidatesTokenCount` no son "caracteres" ni "palabras" — son el conteo real de tokens según el tokenizador propio de ese modelo. Por eso el mismo correo puede costar una cantidad distinta de tokens en Claude que en Gemini: cada uno tiene su propio vocabulario entrenado.

Si quieres ver el tokenizador en acción, tanto Anthropic como Google tienen herramientas públicas para contar tokens de un texto sin hacer una llamada real a la API (útil para estimar costos antes de correr el flujo con muchos correos).

No exactamente — el formato `"2026-09-28"` (ISO 8601, `AAAA-MM-DD`) es justamente el que Airtable espera para un campo tipo **Date**, así que no es un problema de "texto vs. fecha" en el sentido general. El problema es más específico: la API de Airtable es estricta y solo acepta el valor si coincide **exactamente** con la configuración del campo en la tabla (por ejemplo, si el campo tiene activada la opción "Include a time" pero le envías solo la fecha sin hora, lo rechaza; o si el formato de visualización configurado no coincide con el que llega).

## Alternativa (si quieres evitar Typecast)

Revisa en Airtable la configuración del campo **Fecha** (ícono de editar campo → Format): confirma si tiene activado "Include a time". Si es así, tendrías que enviar el valor con hora incluida, por ejemplo:
```
{{ $json.Fecha }}T00:00:00.000Z
```

## Otro problema que veo en tu captura, sin relación con este error

El campo **Asunto** está mapeado incorrectamente:
```
{{ $json.Resumen }}
```
Debería ser:
```
{{ $json.Asunto }}
```
Ahora mismo el "Asunto" en Airtable se llenaría con el contenido del resumen, no con el asunto real del correo. Corrígelo mientras estás en este mapeo manual — es el mismo patrón de error que venías arrastrando con los otros campos. Como comenté antes, si cambias a **Map Automatically**, este tipo de desajustes desaparece porque el nombre del campo decide el mapeo, sin depender de que revises cada expresión a mano.

La opción **Typecast** se agrega justo ahí, en la sección **Options** que ves al final del mapeo de campos.

## Pasos

1. Pulsa **+ Add option** (el botón que ves en tu captura, debajo de "Options").
2. Se abre una lista desplegable con las opciones disponibles para este nodo.
3. Busca y selecciona **Typecast**.
4. Aparecerá un interruptor (toggle) — actívalo (ON).
5. Pulsa **Execute step** de nuevo.

Esto le da a Airtable permiso para convertir automáticamente los valores al tipo exacto que espera cada campo (fechas, selecciones únicas, etc.), en vez de rechazarlos por una diferencia de formato.
